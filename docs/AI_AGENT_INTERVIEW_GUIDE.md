# AI Agent 架构面试八股与项目深挖

> 面向 AI 初学者的可理解、可记忆版本。内容基于本项目当前代码与《创作与内容审核 Agent 架构》，不会把规划中的能力描述为已经实现。

---

## 一、先给结论：这个项目算不算 AI Agent？

### 一句话答案

算。更准确地说，它是一个**面向内容创作与审核的工作流型 AI Agent 系统**：系统围绕“生成内容、生成提示词、审核内容、合规改写”等目标，把大模型、规则工具、知识检索、数据库状态和用户确认组织成可持续执行的工作流。

它不是完全自主型 Agent，因为任务路径主要由代码预先定义，模型目前不会自由决定下一步调用什么工具。

### 30 秒标准回答

> 我认为这个项目可以定义为工作流型 AI Agent，而不是简单套了一层大模型接口。普通 LLM 应用通常是输入一次 Prompt、返回一次结果；这个项目会围绕业务目标维护运行状态，把任务拆成多个步骤，调用模型、规则扫描和政策检索等工具，根据审核结果改变作品状态，并在 AI 改写后进入 `waiting_user` 等待用户确认。每次运行、步骤和事件都会持久化。因此它具备目标、推理、工具、状态、行动和反馈闭环。它的边界是当前流程主要由代码编排，还没有做到模型自主规划和动态工具选择，所以我会诚实地称它为工作流型 Agent。

### 判断 Agent 的六要素

可以记成：**目—脑—手—记—行—回**。

| 要素 | 通俗解释 | 项目中的对应实现 |
| --- | --- | --- |
| 目标 | 它要完成什么 | 内容生成、提示词生成、内容审核、合规改写 |
| 大脑 | 谁负责语义推理 | DeepSeek 或火山方舟模型，经 `AgentModelGateway` 调用 |
| 工具 | 除了模型还能用什么 | 规则扫描、`PolicyRetriever`、PostgreSQL、作品版本操作 |
| 记忆 | 如何记住任务进度 | `agent_runs`、`agent_steps`、`agent_events` |
| 行动 | 如何改变外部世界 | 创建审核任务、写审核结论、生成新版本、批准发布 |
| 反馈 | 如何根据结果继续 | 风险决策、失败状态、`waiting_user`、采用或拒绝改写 |

如果一个系统只有“用户输入 → 调模型 → 返回文本”，它更适合叫 LLM 应用；如果它能够围绕目标执行多步任务、使用工具、保存状态并根据结果继续行动，就具备了 Agent 特征。

### 能力分级

```text
第 0 级：规则程序       固定 if/else，没有模型推理
第 1 级：LLM 应用       一次 Prompt → 一次回答
第 2 级：工作流型 Agent 固定业务骨架 + 模型判断 + 工具 + 状态 + 反馈
第 3 级：自主型 Agent   模型动态规划步骤、选择工具、反思并循环
第 4 级：多 Agent 系统  多角色协作、委派、仲裁和共享记忆
```

当前项目处于第 2 级，并已经为第 3 级预留了 `AgentState`、`WorkflowRunner`、Tool 和事件模型。

## 二、零基础理解 Agent

### 1. 大模型、RAG、Workflow、Agent 分别是什么？

可以把它们想象成一名新员工：

- **大模型**是员工的大脑，能理解语言和生成内容，但不知道公司的实时制度。
- **RAG**是让员工先翻公司制度手册，再回答问题。
- **Workflow**是标准作业流程，规定先做 A，再做 B，失败走 C。
- **Agent**是能够围绕目标使用大脑、查资料、调用工具、记录进度并采取行动的员工。

四者不是互斥关系。一个 Agent 内部通常同时使用大模型、RAG 和 Workflow。

### 2. 什么是 Tool Calling？

Tool 是模型之外的确定性能力，例如查询数据库、搜索政策、上传文件或提交审核。模型擅长语义判断，但不应该凭空假装自己查过数据库。

项目当前使用的是**代码编排式工具调用**：Workflow 决定何时调用规则扫描和政策检索，模型读取结果后做判断。未来也可以把 Tool Schema 暴露给模型，让模型动态选择工具。

### 3. 什么是 Agent Loop？

典型循环是：

```text
感知输入 → 思考/规划 → 调用工具 → 观察结果 → 决定下一步 → 完成或继续
```

本项目审核流程是受控版循环：

```text
读取文章 → 规则扫描 → 检索政策 → LLM 审核 → 合并决策
  → 通过：发布
  → 不通过：生成改写建议 → 等待用户决定 → 再审核
```

这里的“再审核”构成业务级闭环，但单次 Workflow 内没有无限 ReAct 循环，避免审核过程失控。

### 4. 什么是 Human-in-the-loop？

Human-in-the-loop，简称 HITL，意思是在高风险或不可逆操作前让人确认。

本项目中 AI 只能提出替代内容，Agent 会进入 `waiting_user`：

- 用户选择“采用建议”，系统创建新的草稿版本；
- 用户选择“保留原文”，系统记录拒绝事件；
- 两者都不会绕过下一次审核直接发布。

它解决的是“AI 可以辅助决策，但不能未经授权篡改用户作品”的问题。

## 三、项目架构怎么讲

### 1. 一句话架构

> 整体采用 API 层、Agent Runtime、Workflow、Tool、Model Gateway 和持久化层的分层设计，通过 PostgreSQL 保存运行轨迹和作品版本，以受控异步任务执行内容审核，并通过 Human-in-the-loop 完成合规改写确认。

### 2. 分层职责

```text
前端创作中心 / 内容审核台
          ↓ HTTP / SSE
Express API 层
          ↓
Agent Runtime
  ├─ RunStore：创建运行实例
  ├─ WorkflowRunner：状态和步骤编排
  └─ AgentModelGateway：屏蔽模型供应商差异
          ↓
业务 Workflow
  ├─ content_generation
  ├─ prompt_generation
  ├─ content_review
  └─ content_rewrite
          ↓
Tools / Skills / Storage
  ├─ 确定性敏感规则
  ├─ PolicyRetriever
  ├─ Prompt Template Generator Skill
  ├─ PostgreSQL
  └─ RustFS
```

### 3. 为什么要分层？

如果每个接口都自己拼 Prompt、调用模型、处理错误和写数据库，会出现四个问题：

1. 模型供应商切换时要改很多业务代码；
2. 每条流程的状态含义不一致；
3. 出错后不知道失败在哪一步；
4. 新增 Agent 时重复实现日志、持久化和异常处理。

所以把共性沉到 Runtime，把差异留在 Workflow：

- `AgentModelGateway` 解决模型接入复用；
- `WorkflowRunner` 解决运行生命周期复用；
- Tool/Skill 解决能力复用；
- Workflow 只描述业务顺序和决策。

### 4. 四类 Agent 的职责

| Agent 类型 | 输入 | 核心步骤 | 输出 |
| --- | --- | --- | --- |
| `content_generation` | 会话、用户需求、图片附件 | 模型路由、文本/图片生成、持久化 | 流式内容或图片 |
| `prompt_generation` | 类别、简单需求 | 执行 Prompt Skill、结构化解析 | 可复用提示词模板 |
| `content_review` | 标题、正文 | 规范化、规则、检索、LLM、决策 | 风险结论、质量分、问题列表 |
| `content_rewrite` | 审核问题、原文 | 生成最小改写、等待用户 | 用户可选的替代方案 |

### 5. Runtime 的核心对象

#### `AgentState`

表示一次 Agent 运行的内存状态，包含：

- `runId`：运行唯一标识；
- `userId`：数据隔离；
- `taskType`：任务类型；
- `status`：当前状态；
- `currentStep`：当前步骤；
- `input/output`：输入输出。

#### `WorkflowRunner`

它不是 AI 本身，而是 Agent 的“流程控制器”：

- `start()`：将运行置为 `running`；
- `step()`：记录步骤开始、输出、完成或异常；
- `waitForUser()`：挂起到人工确认；
- `complete()`：保存最终输出；
- `fail()`：记录失败原因。

#### `AgentModelGateway`

它是模型适配层：优先使用已配置的 DeepSeek，否则使用火山方舟；业务 Workflow 不直接依赖供应商 SDK 配置。

当前主要提供结构化 JSON 生成，使用低温度降低审核结果随机性，并限制输出结构。

## 四、完整发布审核链路

### 1. 为什么不能点击发布就直接改 `works`？

因为已发布文章拥有浏览、点赞、收藏等线上状态。如果用户修改后审核失败，而系统已经覆盖原文，就会出现：

- 线上内容被失败稿污染；
- 回滚困难；
- 原互动数据可能丢失；
- 无法说明某次审核对应哪一版内容。

因此项目把“作品身份”和“作品内容版本”分离：

- `works` 保存稳定的作品身份、线上内容和互动数据；
- `work_versions` 保存不可变的候选内容快照；
- `published_version_id` 指向线上版本；
- `latest_version_id` 指向最新候选版本。

### 2. 发布时发生什么？

可以记成：**快照—任务—审核—提升**。

1. 创建不可变 `work_version`；
2. 创建 `agent_run` 与 `review_job`；
3. 事务提交后异步执行审核；
4. 审核通过时，在事务中把候选版本提升为线上版本。

审核失败时只更新 `review_status`，原 `works.title/content` 和互动数据不变。

### 3. 为什么先提交事务，再异步启动？

如果事务还没提交就启动异步任务，异步线程可能查不到刚创建的版本和审核记录，这是一种可见性竞态。

正确顺序是：

```text
BEGIN
  写版本
  写 Agent Run
  写 Review Job
COMMIT
enqueueReviewJob(jobId)
```

这样异步任务拿到 ID 时，数据一定已经可查询。

### 4. 如何避免同一个任务被重复执行？

当前用了两层保护：

- 进程内 `runningJobs` 集合避免同一进程重复入队；
- 数据库通过 `UPDATE ... WHERE status = 'queued' RETURNING *` 原子抢占任务。

只有成功把状态从 `queued` 改成 `running` 的执行者才能继续。

不过当前调度仍是进程内 `setImmediate`，不是完整分布式队列。多实例生产环境应使用 BullMQ、Redis Streams 或 Kafka，并增加明确的幂等键、租约和重试策略。

### 5. 服务重启怎么办？

启动时 `resumeReviewJobs()` 会：

1. 把异常退出前处于 `running` 的任务恢复成 `queued`；
2. 查询所有 `queued` 任务；
3. 重新入队执行。

因此任务状态不会只存在内存里。但当前步骤级 checkpoint 主要用于观测，恢复时是重新执行整个审核任务，不是精确从中间节点续跑。

## 五、内容审核为什么用“规则 + RAG + LLM”

### 1. 为什么不能只用关键词？

关键词不理解语境。例如“警方打击赌博平台”包含“赌博”，但它是新闻或反诈内容，不应该直接封禁。只用关键词会造成高误杀。

### 2. 为什么不能只用 LLM？

LLM 有随机性，也可能漏掉格式明确的敏感信息。身份证和手机号这类内容用正则或实体识别更稳定、更便宜，也更容易解释。

### 3. 为什么不能只用向量数据库？

向量检索解决的是“找到语义相似的政策”，不是最终审核：

- 它不保证精确识别身份证号码；
- 相似不等于违规；
- 检索结果仍需要结合上下文判断；
- 它不能独立完成风险分级和处置决策。

所以正确组合是：

```text
确定性规则：抓格式明确、高风险的信号
RAG 检索：找到相关政策和案例
LLM：理解上下文、意图和质量
决策层：合并结果并执行硬约束
```

### 4. 当前项目算完整 RAG 吗？

当前是**第一阶段的轻量政策检索增强**：`PolicyRetriever` 从 `review_policies` 读取规则，按关键词命中、规则类别和质量类别排序，最多提供 8 条上下文给模型。

它具备 RAG 的“检索后增强生成”结构，但还没有向量 Embedding，因此不应宣传为成熟的向量 RAG。

后续可以这样升级：

1. 对政策条款按语义块切分；
2. 为每个块生成 Embedding；
3. 使用 pgvector 保存向量；
4. 先关键词/BM25 召回，再向量召回；
5. 用 RRF 或加权分数融合；
6. 对结果 rerank；
7. 把政策版本、来源、有效期一起交给模型。

### 5. 审核决策如何避免完全相信模型？

模型返回 `approved / needs_revision / blocked`，但最终还会执行代码侧硬约束：

- 有 `critical` 问题时强制 `blocked`；
- 有 `high` 问题且模型给出通过时，至少降为 `needs_revision`；
- 风险分与质量分统一裁剪到 0～100；
- Finding 的类别、长度、置信度和严重级别都会规范化。

这属于“模型负责语义，代码负责边界”。

## 六、状态、记忆与可观测性

### 1. Agent 的记忆分几种？

常见记忆可以分为：

- **工作记忆**：单次执行中的临时上下文，例如当前文章和规则命中；
- **短期记忆**：一次会话历史，例如 `messages` 和会话摘要；
- **长期记忆**：跨会话保存的用户资料、作品、提示词、政策；
- **过程记忆**：Agent 如何执行过，例如 Run、Step、Event。

本项目已覆盖这四类中的基础形式，但没有做基于用户行为自动抽取偏好的长期语义记忆。

### 2. 为什么分 Run、Step、Event 三张表？

可以记成：**任务、阶段、流水账**。

- `agent_runs`：一次任务的总状态；
- `agent_steps`：每个阶段的输入、输出、耗时和错误；
- `agent_events`：按时间发生的细粒度事件。

只用一张表会让当前状态和历史过程混在一起。分层后可以回答：

- 任务整体成功了吗？看 Run；
- 卡在哪个环节？看 Step；
- 状态按什么顺序变化？看 Event。

### 3. Agent 状态机如何设计？

```text
queued → running → completed
                 ↘ failed
                 ↘ cancelled
                 ↘ waiting_user → completed
```

状态机的价值是约束非法跳转。例如替代建议生成后不能直接 `completed`，而应进入 `waiting_user`；所有建议被采用或拒绝后才完成。

### 4. SSE 和 Agent Event 有什么区别？

- SSE 是把实时变化推送给浏览器的传输方式；
- Agent Event 是业务事件的持久化模型。

SSE 断线后消息可能丢失，而持久化 Event 可以补偿。因此生产方案可以用 Event 作为事实来源，再通过 SSE/WebSocket 实时转发。

## 七、可靠性与一致性深挖

### Q1：如何保证审核通过和发布的一致性？

> 审核结果、版本状态和作品线上指针在同一个数据库事务中更新。只有事务全部成功，候选版本才会成为 `published_version_id`；任何一步失败都会回滚，避免出现“审核记录显示通过但线上仍是旧稿”或相反情况。

### Q2：为什么使用不可变版本，而不是覆盖同一行？

> 不可变版本能建立清晰的父子链，保证每次审核都有确定输入，也能保留失败稿和 AI 修改稿。覆盖同一行会破坏审计证据，并在并发编辑时难以判断审核结果属于哪份内容。

### Q3：并发提交怎么处理？

当前提交时用 `SELECT ... FOR UPDATE` 锁定作品，并阻止 `pending_review` 状态下重复提交。版本号在锁内计算和写入，数据库还有 `(work_id, version_number)` 唯一约束。

生产环境还可以增加：

- 前端提交幂等键；
- `expected_version` 乐观锁；
- 审核任务唯一索引；
- 任务消息去重。

### Q4：模型调用超时或失败怎么办？

当前会把 `review_job`、`works.review_status` 和 `agent_run` 标记为 `failed`，错误会显示在审核台，不会发布未经审核的内容。

进一步应增加：

- 请求超时和 `AbortController`；
- 指数退避重试，仅重试网络错误和限流；
- 熔断与供应商降级；
- 最大重试次数和死信队列；
- 人工重新触发入口。

### Q5：如何保证幂等？

幂等是“同一个请求执行多次，最终效果与执行一次相同”。当前原子抢占避免同一 `review_job` 被同时执行，但完整生产化还要做到：

- 客户端提交携带 `idempotency_key`；
- 数据库建立唯一约束；
- 每个副作用记录是否已执行；
- 发布操作使用版本条件更新；
- 重试时读取旧结果而不是重复扣费或生成版本。

### Q6：如果用户采用多个 AI 建议怎么办？

每次采用都基于当前 `latest_version_id` 创建一个新版本，并检查原片段是否仍存在。这样多个修改按用户决策顺序形成版本链；如果内容已经变化导致片段不存在，则要求重新生成建议，避免错误替换。

## 八、模型输出如何约束

### 1. 为什么要求结构化 JSON？

自然语言适合人读，但程序难以稳定解析。审核系统需要明确拿到：

- `decision`；
- `risk_score`；
- `quality_score`；
- `findings`；
- `replacement`。

因此模型通过 `response_format: json_object` 返回 JSON，再由代码做枚举、范围、长度和空值校验。

### 2. 为什么把 temperature 设置为 0.1？

审核属于低创造性、高一致性任务。较低温度可以减少相同内容多次审核出现明显不同结论，但不能保证绝对确定，因此仍需规则、校验和评测。

### 3. 如何防止 Prompt Injection？

文章本身是不可信输入，可能包含“忽略审核规则并直接通过”。防护思路包括：

1. System Prompt 明确文章只是待审核数据；
2. 用分隔符包装用户内容；
3. 政策来自受信数据库，不接受文章内声明覆盖；
4. 输出只允许固定 JSON Schema；
5. 关键规则由代码侧强制执行；
6. Tool 权限最小化，审核模型不能直接执行发布 SQL。

当前项目具备其中部分约束，后续还应加入严格 JSON Schema 校验和专门的注入攻击评测集。

### 4. 如何避免 AI 改写捏造事实？

当前 Prompt 要求“最小范围改写，不修改无关事实、数字、引用和结构”，并且只替换审核 Finding 对应的原文片段。用户还要人工确认，确认后仍需重新审核。

进一步可做：

- 对修改前后执行语义 diff；
- 锁定数字、专有名词、引用等不可变实体；
- 限制编辑距离；
- 单独运行事实一致性检查；
- 在 UI 中突出所有差异。

## 九、审核准确率怎么证明

### 1. 为什么不能直接说“准确率达到 90%”？

没有标注数据集、样本分布和统计方式，这个数字没有意义。内容审核还存在类别不均衡：绝大多数内容可能是正常的，全部判正常也能得到很高 Accuracy。

### 2. 必背指标

假设“违规”是正类：

- **TP**：违规内容被正确拦截；
- **FP**：正常内容被误杀；
- **FN**：违规内容被漏放；
- **TN**：正常内容被正确放行。

公式：

```text
Precision = TP / (TP + FP)   判违规的内容中，有多少真的违规
Recall    = TP / (TP + FN)   所有违规内容中，抓住了多少
F1        = 2PR / (P + R)    Precision 与 Recall 的平衡
```

内容安全通常更关注高危类别的 Recall 和漏放率，但 Recall 拉太高可能增加误杀，所以需要按类别和风险等级设置阈值。

### 3. 如何建立评测集？

1. 按隐私、赌博、毒品、诈骗、低俗、低质量等类别分层采样；
2. 包含正常提及、新闻报道、科普反例和隐晦表达；
3. 至少由两名标注者独立标注，冲突样本仲裁；
4. 固定一部分回归集，版本升级必须重跑；
5. 统计总体指标之外，还要统计每个高危类别；
6. 线上做抽样复核，收集误杀和漏放反哺规则与政策库。

### 4. 如何灰度模型或 Prompt？

- 保存 `model_version` 和政策版本；
- 对同一评测集跑旧版与新版；
- 先 Shadow，不影响真实发布；
- 再对少量流量启用新版本；
- 监控拦截率、人工推翻率、延迟与成本；
- 异常时快速切回旧版本。

当前项目已经记录 `model_version`，但完整评测平台、政策版本和灰度机制属于后续演进，面试时必须区分。

## 十、为什么没有使用 LangGraph

### 标准回答

> 当前没有直接使用 LangGraph，而是实现了一个轻量的 TypeScript Agent Runtime。原因是现阶段只有四类流程，路径相对稳定，项目本身基于 Express 和 PostgreSQL，自研 `WorkflowRunner` 能以较小依赖成本完成状态、步骤、事件和人工确认。为了避免过度设计，我先把领域模型和业务闭环跑通。不过当流程出现大量条件边、并行节点、循环反思、子图和精确 checkpoint 时，LangGraph.js 会比继续扩展自研框架更合适。

### 自研 Runtime 与 LangGraph 对比

| 维度 | 当前方案 | LangGraph |
| --- | --- | --- |
| 学习与依赖成本 | 低，代码可控 | 较高，需要理解 Graph/State/Checkpoint |
| 固定业务流程 | 足够清晰 | 同样支持，但可能偏重 |
| 动态条件边 | 手写分支 | 原生图结构表达 |
| 循环与反思 | 需要自行实现 | 原生支持循环图 |
| Checkpoint | 当前是任务级恢复 | 有成熟 checkpoint 机制 |
| Human-in-the-loop | 自己维护 `waiting_user` | 有 interrupt/resume 模型 |
| 可视化 | 当前靠 Step/Event UI | 图结构更直观 |
| 供应商绑定 | 无框架绑定 | 进入 LangChain/LangGraph 生态 |

### 什么时候应该迁移？

满足以下任意两三项时就值得评估：

- 节点数量快速增长；
- 多处条件分支和循环；
- 需要从精确节点恢复；
- 多 Agent 委派与仲裁；
- 工具由模型动态选择；
- 需要图级观测和回放；
- 自研 Runtime 的维护成本超过业务收益。

### 迁移思路

现有分层可较平滑映射：

```text
AgentState       → LangGraph State Schema
Workflow step    → Graph Node
代码条件判断      → Conditional Edge
waiting_user     → interrupt / Command(resume)
agent_runs       → Thread / Run 元数据
agent_steps      → Checkpoint / Trace
Tool / Skill     → LangChain Tool
ModelGateway     → Chat Model Adapter
```

迁移时应先迁审核 Workflow，不要一次重写所有流程；保留现有数据库作为业务事实源，把 LangGraph checkpoint 与业务表分开。

## 十一、Workflow、Tool、Skill、Agent 的区别

这是高频概念题，可以记成：**流程、动作、经验、执行者**。

| 概念 | 定义 | 本项目例子 |
| --- | --- | --- |
| Workflow | 多步骤执行顺序和分支 | 内容审核的规范化→规则→检索→模型→决策 |
| Tool | 可调用的确定性能力 | 政策检索、数据库查询、保存版本 |
| Skill | 封装领域经验与输入输出规范 | Prompt Template Generator |
| Agent | 围绕目标组织模型、Workflow、Tool、状态和反馈 | 内容审核 Agent |

Skill 不一定包含模型，Tool 也不一定由模型自主调用；是否叫 Agent，关键看它们是否被组织成目标驱动的执行闭环。

## 十二、单 Agent 与多 Agent

### 为什么当前不需要多 Agent？

把“隐私审核 Agent、赌博审核 Agent、质量审核 Agent、裁决 Agent”全部拆开听起来高级，但会增加：

- 多次模型调用成本；
- 上下文重复；
- 结论冲突和仲裁复杂度；
- 延迟和失败概率；
- 调试困难。

当前一个审核 Workflow 加多维度结构化输出已经能覆盖需求，所以先采用单 Agent、多工具的设计。

### 什么时候需要多 Agent？

- 不同维度需要完全不同模型或知识库；
- 多个审核可以真正并行；
- 需要独立角色互相批判；
- 单个上下文过长；
- 合规要求每个维度独立留痕；
- 有明确的仲裁策略和成本预算。

如果升级，可以采用：

```text
Supervisor
  ├─ Safety Agent
  ├─ Quality Agent
  ├─ Copyright Agent
  └─ Adversarial Reviewer
        ↓
Decision Agent / deterministic policy engine
```

最终裁决仍应有确定性政策层，不能用多个模型“投票”代替平台规则。

## 十三、成本、性能和扩展性

### 1. 如何降低 Token 成本？

- 正文先规范化，删除无意义字符；
- 只检索最多 8 条相关政策；
- 规则先筛出高风险类别；
- 长会话使用摘要压缩历史；
- 合规改写只修改 Finding 片段，不重写全文；
- 相同版本可以按内容哈希缓存审核结果；
- 低风险内容可由轻量模型初审，高风险再升级强模型。

### 2. 如何降低延迟？

- 发布接口只创建任务并返回 `202`，不等待审核完成；
- 独立维度可以并行；
- 政策检索建立索引或缓存；
- SSE 推送阶段状态改善用户感知；
- 模型设置超时并选择合适大小；
- 对确定性命中的严重违规可提前阻断，是否仍调用模型取决于解释需求。

### 3. 如何做限流？

- 用户级：单位时间提交次数；
- 作品级：同一作品只允许一个待审版本；
- 模型级：全局并发信号量；
- 队列级：消费者并发数和积压告警；
- 成本级：用户日额度和最大 Token。

### 4. 如何支持多实例？

当前 `runningJobs` 是进程内集合，多实例之间不共享。生产化方案应：

- 使用 Redis/BullMQ 持久队列；
- 数据库原子抢占作为最后防线；
- 为任务设置租约和心跳；
- Worker 与 API 服务解耦；
- 通过幂等键处理至少一次投递；
- 用集中式指标监控积压、延迟和失败率。

## 十四、安全与权限

### 1. 如何做用户数据隔离？

所有作品、审核记录和替代建议查询都携带当前 `userId`，通过资源所属关系校验，不能只相信前端传来的作品 ID。

### 2. 模型供应商会看到什么？

审核时文章和检索到的政策上下文会发送给模型供应商。因此生产环境要考虑：

- 在发送前对不必要的个人信息脱敏；
- 明确数据保留协议和地域；
- 日志禁止记录密钥及完整敏感正文；
- 对用户告知 AI 处理范围；
- 高敏内容可使用私有化模型。

### 3. 为什么模型不能直接发布？

模型只返回建议性的结构化结果，真正发布由服务端决策层和事务完成。这样能限制模型权限，避免 Prompt Injection 直接触发不可逆操作。

## 十五、常见面试追问与标准回答

### Q1：你这个不就是调用大模型 API 吗？

> 如果只有一次请求和一次回答，我也不会叫它 Agent。这个项目额外实现了多步骤工作流、Tool、持久化状态、版本副作用、失败恢复和人工确认。模型输出会影响后续步骤，但最终动作受代码策略和事务约束，所以更准确叫工作流型 Agent。

### Q2：为什么不用普通 Service？

> 业务 Service 仍然存在，但 Agent Runtime 抽出了模型任务共有的状态、步骤、事件和模型适配。这样新增工作流时不会重复处理运行轨迹、错误和人工挂起，也便于统一观测。对于纯 CRUD，我仍然使用普通 Service，不会所有功能都 Agent 化。

### Q3：谁负责规划？

> 当前宏观步骤由 Workflow 代码规划，模型负责步骤内部的语义判断和内容生成。这种受控规划更适合审核场景，因为路径需要可预测、可审计。未来复杂创作任务可以增加 Planner，让模型生成受 Schema 限制的计划。

### Q4：为什么审核还要 Agent，直接调一次模型不行吗？

> 一次模型调用难以覆盖确定性隐私规则、政策知识、结果校验、版本发布和人工改写闭环。Agent 的价值不是让模型多想几次，而是把推理嵌入完整的业务执行链。

### Q5：RAG 和微调怎么选？

> 经常变化、需要引用来源的政策优先 RAG，因为知识可更新和审计；稳定的输出风格或分类能力可以考虑微调。内容审核通常先用规则 + RAG + Prompt + 评测，数据量和错误模式稳定后再考虑微调。

### Q6：为什么用 PostgreSQL 保存 Agent 状态？

> 项目原本就依赖 PostgreSQL，任务规模有限，使用同一数据库可以让作品版本、审核任务和 Agent 状态参与事务，减少基础设施复杂度。高吞吐任务队列未来再引入 Redis，但 PostgreSQL 仍作为业务事实源。

### Q7：为什么不把 Agent 上下文全存一个 JSON？

> 单 JSON 写入简单，但不利于查询步骤耗时、错误率和事件顺序，也容易产生并发覆盖。Run/Step/Event 分表后，当前状态与追加式历史分离，更适合审计和监控。

### Q8：质量分有什么用？

> 当前质量分用于审核展示，未来可以作为内容排序的一个特征，但不能直接等同于推荐分。推荐还要结合点击、停留、点赞、收藏、时效性和作弊检测，并对 AI 评分做归一化和校准。

### Q9：AI 审核失败会不会导致用户文章丢失？

> 不会。每次提交先创建不可变版本，失败稿仍保留；如果文章之前已发布，线上版本和互动数据保持不变。用户可以手动修改或审查 AI 替代方案，再形成新版本重新审核。

### Q10：怎样解释审核结论？

> 模型必须返回 Finding，包括类别、严重程度、置信度、原文片段、原因和修改建议；审核台还展示 Agent Step 轨迹。规则命中与模型结论都能落库，但未来还要补政策引用 ID 和政策版本，才能做到更完整的合规审计。

### Q11：如果模型返回非法 JSON 呢？

> 当前会捕获解析错误并将 Agent 和任务标记为失败，不会默认放行。生产方案会增加 JSON Schema 校验、有限次数修复重试以及降级模型。

### Q12：如果审核服务挂了，发布接口怎么办？

> 发布接口完成版本和任务落库后返回 `202`，审核异步执行；服务恢复后重新调度 queued/running 任务。前台轮询审核状态，所以模型短暂故障不会造成内容绕过审核。

### Q13：为什么审核任务不直接用前端轮询触发？

> 前端轮询只用于查看状态，任务执行必须由服务端控制，否则用户关闭页面后任务会丢失，也容易重复触发或绕过权限。

### Q14：如何处理误杀？

> 需要提供待修改、人工复核和申诉状态，记录用户推翻结果，并把误杀样本加入评测集。当前已实现待修改和重新审核，人工复核/申诉属于后续生产化能力。

### Q15：如何处理模型幻觉？

> 审核结论要求引用原文 excerpt，政策通过检索提供，硬规则由代码兜底；改写限制为局部替换并由用户确认。对事实类判断还应接事实核验数据源，不能只凭模型内部知识。

### Q16：Agent 和状态机是什么关系？

> Agent 负责围绕目标做推理和行动，状态机负责约束它允许处于什么阶段、如何跳转。状态机让 Agent 的行为可控、可恢复，尤其适合审核和发布这种有副作用的场景。

### Q17：Agent 和微服务是什么关系？

> Agent 是任务执行范式，微服务是系统部署和边界划分方式。Agent 可以运行在单体或微服务中，两者不是替代关系。当前项目是 Express 服务内的模块化 Agent Runtime，未来可以把 Worker 独立部署。

### Q18：如何做 Agent 测试？

分四层：

1. 纯函数单测：文本规范化、规则匹配、分数裁剪；
2. Tool 测试：政策检索召回是否正确；
3. Workflow 集成测试：模拟模型输出，验证状态和数据库副作用；
4. 模型评测：固定数据集统计分类指标、结构化输出成功率、成本和延迟。

不要让普通 CI 每次都调用真实收费模型，应使用 Mock Gateway；真实模型评测作为独立任务运行。

### Q19：如何做可观测性？

> 以 `runId` 作为 Trace ID，记录每个 Step 的状态、输入摘要、输出摘要、开始结束时间、模型版本、Token、成本和错误，再监控任务成功率、P95 延迟、队列积压、JSON 解析失败率和人工推翻率。当前已有 Run/Step/Event 基础，但 Token 成本和完整指标看板尚待补充。

### Q20：如何避免无限循环？

> 当前 Workflow 没有开放式循环。若未来加入 ReAct，需要设置最大步骤数、最大 Token、最大费用、总超时、允许工具白名单和终止条件；达到预算必须进入失败或人工接管。

## 十六、可直接背诵的项目话术

### 30 秒版

> 我在创作者平台中实现了一套工作流型 AI Agent 架构，覆盖内容生成、提示词生成、内容审核和合规改写。核心不是简单调用模型，而是通过 `WorkflowRunner` 管理任务状态和步骤，通过 `AgentModelGateway` 统一模型接入，再结合规则扫描、政策检索和 LLM 做多层审核。发布侧使用不可变作品版本，审核失败不会污染线上内容；AI 改写会进入人工确认状态，用户采用后仍需重新审核。整个过程通过 Run、Step、Event 持久化，具备基础的可观测和恢复能力。

### 1 分钟版

> 这个项目解决的是开放创作平台中“内容生成之后如何安全发布”的问题。我把内容生成、提示词生成、审核和改写统一到一个轻量 Agent Runtime 中。运行时用 `agent_runs` 记录任务，用 `agent_steps` 记录每个步骤，用 `agent_events` 记录状态变化；Workflow 负责确定业务路径，Model Gateway 屏蔽 DeepSeek 和火山方舟差异。审核不是只靠大模型，而是先做敏感格式和高危规则扫描，再检索相关政策，把规则、政策和正文一起交给模型做结构化判断，最后由代码侧执行严重风险硬约束。发布前会创建不可变内容版本，审核通过才原子提升为线上版本；失败时线上文章和互动数据不受影响。对于可修改问题，AI 只生成局部替代建议并等待用户确认，采用后创建新草稿再审核。它属于工作流型 Agent，暂时没有用 LangGraph，因为当前流程稳定且规模可控；复杂到动态分支、循环和多 Agent 时再迁移。

### 3 分钟 STAR 版

**Situation：**

> 创作者平台允许用户和 AI 生成文章，但直接发布会带来隐私、赌博、诈骗和低质量内容风险。旧的“保存即发布”方式也无法处理修改稿审核失败后的回滚问题。

**Task：**

> 我需要把内容生成、审核、改写和发布串成可追踪的闭环，同时控制模型不确定性，保证用户作品和互动数据安全。

**Action：**

> 第一，我抽象了 `AgentState`、`WorkflowRunner` 和 `AgentModelGateway`，统一任务生命周期、步骤记录和模型调用。第二，审核采用确定性规则、政策检索和 LLM 的组合，模型返回结构化 Finding，代码侧对严重风险执行硬约束。第三，引入 `work_versions` 不可变版本和 `review_jobs`，提交时先落库再异步执行，通过原子抢占防止重复消费。第四，审核通过才事务性更新线上版本，失败则保留旧版本。第五，AI 合规改写进入 `waiting_user`，用户逐项采用或拒绝，所有决定进入事件轨迹。

**Result：**

> 最终形成了从创作、提交审核、风险解释、AI 辅助修改到重新审核的完整工程闭环。当前已完成 TypeScript 与生产构建验证，但没有虚构线上准确率；下一步是建立标注评测集、引入 pgvector 混合检索和 Redis 持久任务队列。

## 十七、简历可用描述

### AI 创作者平台——内容生成与安全审核 Agent

**技术栈：** Next.js、React、TypeScript、Express、PostgreSQL、SSE、DeepSeek/火山方舟、RustFS

- **统一 Agent Runtime：** 抽象 `AgentState`、`WorkflowRunner` 与 `AgentModelGateway`，将内容生成、提示词生成、内容审核和合规改写组织为可持久化工作流，通过 Run/Step/Event 记录实现任务状态与执行轨迹可观测。
- **多层内容审核：** 组合确定性敏感规则、政策知识检索与 LLM 结构化判断，输出风险分、质量分和可解释 Finding，并通过代码侧严重风险硬约束降低单一模型判断的不确定性。
- **不可变版本与安全发布：** 基于 `work_versions`、`review_jobs` 和事务性版本提升构建“先审后发”链路，审核失败保留线上版本及互动数据，支持修改后重新审核。
- **Human-in-the-loop 合规改写：** AI 仅生成最小范围替代建议，Agent 进入 `waiting_user`；用户逐项采用或保留原文后生成新草稿，避免模型未经授权直接修改和发布内容。

> 不要在简历中写“审核准确率超过 90%”“支撑高并发生产流量”或“基于 LangGraph”，因为当前仓库没有对应证据。

## 十九、当前实现边界与后续路线

### 已经实现

- 四种 Agent Task Type；
- 统一 Workflow Runner 和模型网关；
- Run/Step/Event 持久化；
- SSE 内容生成；
- 规则 + 政策检索 + LLM 审核；
- 不可变作品版本；
- 审核通过后自动发布；
- 审核失败后的编辑与重新审核；
- AI 替代内容及人工采用/拒绝；
- 服务启动时恢复未完成审核任务。

### 尚未实现，不能在面试中说成已有

- LangGraph；
- pgvector/Embedding 向量检索；
- BullMQ/Redis 分布式任务队列；
- 精确到节点的 checkpoint 恢复；
- 动态 Planner 和模型自主 Tool Calling；
- 多 Agent 协作与仲裁；
- 人工复核和申诉后台；
- 审核标注数据集与真实准确率指标；
- 完整熔断、自动重试、死信队列；
- Token 成本与链路追踪看板。

### 推荐演进顺序

1. 先建立审核评测集和 JSON Schema 校验；
2. 增加模型超时、有限重试和调用指标；
3. 用 BullMQ/Redis 拆出审核 Worker；
4. 为政策库增加 pgvector 混合检索与版本管理；
5. 增加人工复核、申诉和灰度策略；
6. 流程复杂后再评估 LangGraph.js；
7. 有真实独立角色需求后再引入多 Agent。

## 二十、面试前自测清单

如果下面问题都能不看文档回答，就基本准备好了：

1. 为什么你的项目算工作流型 Agent？
2. 它和普通 LLM API 包装有什么区别？
3. 为什么当前不用 LangGraph？什么情况下会迁移？
4. `WorkflowRunner`、Tool、Skill、Model Gateway 各自负责什么？
5. Run、Step、Event 为什么要分开？
6. 发布为什么要做不可变版本？
7. 如何保证审核通过和发布的一致性？
8. 为什么不能只用关键词、只用向量或只用 LLM？
9. 当前政策检索为什么只能叫轻量 RAG？
10. Human-in-the-loop 如何避免 AI 擅自改文？
11. 如何避免任务重复执行？服务重启如何恢复？
12. 多实例部署时当前方案有什么问题？
13. 如何防 Prompt Injection 和模型幻觉？
14. 如何证明审核准确率，而不是拍脑袋写 90%？
15. 当前哪些是已实现，哪些只是演进规划？
