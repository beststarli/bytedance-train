# AIGC 内容创作与审核平台 · 面试深挖问答

> 本文基于当前仓库代码、`README.md`、`docs/AGENT_ARCHITECTURE.md`、数据库模型与 Git 记录整理。回答采用“候选人可直接复述”的第一人称口径。凡涉及个人职责、线上规模、性能指标的内容，均未擅自编造；面试前请结合真实经历补全。

## 一、项目总览与开场

### Q1：请用 30 秒介绍一下这个项目。

这是一个面向内容创作者的 AIGC 创作与内容治理平台。前端使用 Next.js 16、React 19、TypeScript、Tailwind CSS 和 Zustand，后端使用 Express 5、PostgreSQL、OpenAI 兼容 SDK，并接入火山方舟、DeepSeek 和 RustFS。核心链路不是单纯调用大模型，而是把多轮创作、文生图、素材沉淀、不可变作品版本、规则与 LLM 联合审核、合规改写和用户确认串成闭环。我重点可以展开三部分：SSE 流式创作及中断、版本化审核发布、可追踪的 Agent Workflow。

### Q2：这个项目解决了什么问题？为什么不直接做一个 AI 聊天框？

普通聊天框只解决“生成一次内容”，但真实创作还有上下文管理、图片引用、素材复用、编辑、发布、审核和修改闭环。这个项目把模型能力嵌入内容生命周期：生成结果可导入编辑器，图片要持久化到素材库，发布前形成候选版本并审核，未通过时给出证据和最小改写建议，只有用户确认后才产生新草稿。项目价值因此落在工作流和治理，而不只是模型调用。

### Q3：项目最值得讲的技术亮点是什么？

我会讲五点：第一，基于 SSE 和 `AbortController` 的文本/图片统一流式创作；第二，滑动窗口加历史摘要的长对话上下文管理；第三，不可变 `work_versions` 与线上版本指针隔离；第四，确定性规则、政策检索、LLM 结构化判断和决策合并的多层审核；第五，`WorkflowRunner`、`agent_runs/steps/events` 与 Human-in-the-loop 形成可追踪、可等待用户确认的 Agent Runtime。

### Q4：为什么选择前后端 TypeScript？

项目交互和数据结构较多，TypeScript 能让前后端共享相似的领域语义，降低流式事件、审核结果、作品状态等结构在开发期漂移的风险；Node.js 对 SSE、异步 I/O 和 OpenAI SDK 的集成也比较直接。代价是 CPU 密集任务不适合放在主进程，当前审核和模型调用以 I/O 为主；生产化时会把长任务放到持久队列和独立 Worker。

### Q5：为什么使用 Next.js，而不是纯 React SPA？

Next.js 提供约定式工程结构、构建优化和后续 SSR/SEO 的演进空间，适合内容平台。不过当前核心页面大量依赖登录态、编辑器状态和流式交互，主要仍是客户端组件，所以我不会夸大 SSR 收益。如果只是内部工具，Vite SPA 会更轻；面向公开内容分发时，Next.js 的服务端渲染和元数据能力更有价值。

### Q6：为什么后端选 Express，而不是 NestJS 或 Java Spring Boot？

Express 适合训练营项目快速验证端到端闭环，路由、中间件和 OpenAI SDK 接入成本低。它的代价是模块边界、依赖注入、参数校验和异常治理需要自己约束，当前 `content.ts` 已经偏大。若进入多人长期维护阶段，我会拆分 Controller、Application Service、Repository 和 Worker；需要更强规范时可以迁移到 NestJS，但不会只为了框架名重写业务。

### Q7：项目当前做到什么程度，哪些还不是生产级？

代码已经覆盖登录、创作会话、SSE 文本生成、文生图和素材持久化、作品发布、审核记录、改写建议、采用/拒绝和数据看板等链路。仍需明确的边界是：审核任务目前由进程内 `Set + setImmediate` 驱动，不是持久消息队列；政策检索是关键词与类别匹配，不是向量检索；模型 JSON 只做解析和手工归一化，没有完整 JSON Schema；缺少自动化测试、离线审核评测集和真实压测数据。

## 二、前端深挖

### Q8：前端整体状态是如何划分的？

跨页面且长期存在的状态放在 Zustand，例如用户登录态和编辑器草稿；页面局部的聊天列表、当前消息、附件、发送状态等使用 React state；不需要触发渲染的控制对象，例如当前 `AbortController`、流式聊天 ID、编辑器 DOM 引用放在 `useRef`。划分原则是状态的共享范围和是否参与渲染，而不是把所有内容都塞进全局 Store。

### Q9：为什么选择 Zustand，而不是 Redux 或 Context？

当前全局状态规模不大，Zustand API 简洁、样板代码少，能按 selector 订阅局部状态。Context 适合低频配置，但高频编辑状态容易导致 Provider 子树重渲染；Redux Toolkit 在复杂事件溯源、规范化缓存和大型团队约束上更强，但这个项目暂时不需要它的完整体系。如果状态继续增长，我会先拆 Store slice、增加持久化边界，而不是立即换库。

### Q10：SSE 前端是怎么消费的？为什么不能简单按一次 `read()` 对应一条事件？

前端通过 `fetch` 获取 `ReadableStream`，用 `TextDecoder` 增量解码，把新文本追加到缓冲区，再按 SSE 的空行边界拆帧并解析 `data:` JSON。网络分包与业务事件没有一一对应关系：一次读取可能只有半条 JSON，也可能包含多条事件，所以必须保留残余 buffer。流结束时还要处理未消费尾部，并对 `done/error` 做收口。

### Q11：为什么这里使用 SSE，而不是 WebSocket？

核心场景是客户端发起一次请求、服务端单向持续返回生成进度和内容，SSE 的语义和调试成本更合适，且天然基于 HTTP。WebSocket 更适合高频双向消息、协同编辑或实时房间。这里用 POST 加 fetch 流读取，是因为请求体需要携带创作内容和附件；它不像原生 `EventSource` 那样自动重连，因此断线续传需要额外设计事件 ID 和运行状态查询。

### Q12：如何实现“停止生成”？

前端为每次生成创建 `AbortController`，把 `signal` 传给 fetch；点击停止时调用 `abort()`。后端监听响应连接 `close`，再中止传给模型 SDK的 signal，从而尽量停止上游模型计算。前端捕获 `AbortError`，保留已生成片段并标记中断。需要注意，中断是协作式取消，不保证供应商已经发生的计费完全撤销。

### Q13：如何避免用户连续点击发送产生竞态？

界面用 `sending` 禁用重复发送，并用 ref 记录当前流和控制器。但单靠前端不够，后端仍要做幂等或状态约束。审核提交中，后端通过事务内 `SELECT ... FOR UPDATE` 锁定作品，并检查 `pending_review`，避免同一作品重复进入审核；生成消息目前还可以进一步增加客户端请求 ID 和唯一索引。

### Q14：流式内容如何避免频繁更新导致卡顿？

当前实现会随 chunk 合并消息状态，简单可靠，但 token 很碎时可能频繁渲染。生产优化可以先把 chunk 累积在 ref，在 `requestAnimationFrame` 或 30～50ms 批次内提交一次 state；消息组件用稳定 key 和 `memo` 隔离；Markdown 解析也应节流，完成后再做完整渲染。优化前应先用 React Profiler 定位，而不是凭感觉改。

### Q15：为什么编辑器中需要 Markdown 与 HTML 双向转换？

内容最终以 Markdown 作为可存储、可给模型处理的文本格式，但浏览器可编辑区域更适合用 HTML DOM 交互，所以实现了 Markdown 到编辑器 HTML、DOM 再回到 Markdown 的转换。风险在于自研转换器容易丢失嵌套列表、代码块等复杂语义，也要防止 XSS。若富文本能力继续增长，应使用成熟 AST 管线或编辑器框架，并对渲染 HTML 做白名单净化。

### Q16：前端为什么使用 `requestAnimationFrame`？它与防抖有什么区别？

这里主要用于等待 DOM 提交后再聚焦或调整 textarea 高度，让读写布局靠近下一帧执行。`requestAnimationFrame` 按浏览器绘制节奏调度，不等价于业务防抖；防抖是在连续事件停止一段时间后执行一次，适合自动保存和搜索输入。TODO 中的草稿自动保存应采用“变更检测 + 防抖 + 卸载兜底”，而不是只靠 RAF 计时。

### Q17：登录态刷新时如何做到无感？

后端签发短期 access token 和长期 refresh token；access token 由前端用于 Bearer 鉴权，refresh token 放在 `HttpOnly` Cookie。前端请求前判断 access token 是否临近过期，或收到 401 后调用 refresh，再重放一次原请求。这样减少长期凭证暴露给 JavaScript 的风险。进一步需要处理并发 401 的“刷新风暴”，用单例 Promise 让多个请求共享一次刷新。

### Q18：为什么 refresh token 放 Cookie，access token 没有全放 Cookie？

这是安全和工程便利的折中。`HttpOnly` 能降低 refresh token 被 XSS 直接读取的风险；access token 由前端显式带 Bearer，便于跨 API 使用。Cookie 自动携带会带来 CSRF 关注，所以设置 `SameSite=Lax`、限定 Path，生产环境开启 Secure。更严格方案可以全部采用 HttpOnly Cookie，再配合 CSRF Token。

### Q19：图片附件为什么不能只把外部 URL 直接交给模型？

外部 URL 可能临时失效、需要鉴权，甚至引入 SSRF。项目先校验附件属于当前用户的素材记录，再由后端读取受控对象并转换为 data URL 交给模型；生成结果也从供应商临时 URL 下载后持久化。生产中还应限制 MIME、大小、重定向次数、可访问域和下载超时。

### Q20：前端组件目前有什么可维护性问题？

`createPage.tsx` 承载聊天、SSE、附件、编辑器、素材架和发布等多类职责，文件过大。重构时我会按 use case 拆成 `useStreamingGeneration`、`useChatSession`、`Composer`、`MessageList`、`ArticleEditor` 和 `MaterialShelf`，并把 SSE 协议解析抽成可单测的纯函数。拆分依据应是状态和副作用边界，不是机械按行数拆文件。

### Q21：如何处理错误状态，避免“静默失败”？

流式请求要区分业务错误、网络错误、模型错误和用户主动取消；用户消息应保留，AI 占位消息转为明确错误或“已中断”，并恢复发送状态。全局 API 层统一解析非 2xx 响应和刷新登录态。下一步会加入错误码、可重试标记、Toast 与运行 ID，方便用户重试和后端排查。

### Q22：如果让你给前端补测试，怎么分层？

先测最容易出错的纯逻辑：SSE 半包/粘包解析、Markdown 转换、JWT 到期判断和资源 URL 解析；再用 React Testing Library 测发送、中断、失败、附件引用、审核状态轮询；最后用 Playwright 跑“登录—生成—编辑—提交审核—采用改写”的关键链路。流式接口用可控 fake server，覆盖半截事件和异常终止。

## 三、后端与数据库深挖

### Q23：后端如何组织一次内容生成？

路由先鉴权和校验会话归属，保存用户消息，建立 SSE 响应并创建 `content_generation` Agent Run；`route_model` 步骤根据附件、显式模型类型或关键词选择文本/图片；`generate_content` 调模型并持续推送事件；完成后保存助手消息、更新标题并结束 Run。连接关闭会触发模型取消，失败则记录 Run error 并发送错误事件。

### Q24：为什么先保存用户消息，再调用模型？

这样即使模型失败或用户中断，用户意图仍可恢复和重试，也能保证服务端对话历史是事实来源。代价是可能出现只有用户消息没有助手消息的半完成轮次，因此消息模型最好增加 generation status、request ID 或关联 Agent Run，避免历史重放时误解状态。

### Q25：为什么 SQL 使用参数化查询？动态排序会不会有注入风险？

值全部用 `$1` 等参数绑定，避免输入成为 SQL 语法。排序字段无法作为普通参数绑定，因此代码先用白名单 `Set` 将用户输入映射到固定 `ORDER BY` 片段；只要不直接拼接原始 query，风险可控。表名、列名、排序方向等动态标识符都应采用同样白名单策略。

### Q26：作品发布为什么要设计 `works` 和 `work_versions` 两张表？

`works` 是聚合根和当前展示状态，保存 `latest_version_id`、`published_version_id` 等指针；`work_versions` 保存不可变快照与父版本链。用户编辑已发布作品时只生成新草稿，不覆盖线上正文；只有候选版本审核通过，事务才原子更新线上正文和发布指针。这样可以回溯审核对象，也避免审核期间线上内容被换掉。

### Q27：`latest_version_id` 和 `published_version_id` 有什么区别？

`latest_version_id` 指向最新编辑候选，可能是 draft、pending_review 或 needs_revision；`published_version_id` 只指向当前线上已通过版本。两者分离后，创作者可以继续修改而读者仍看到稳定的已发布版本。这是典型的“工作副本与发布快照”分离。

### Q28：提交审核时为什么需要事务和行锁？

提交包含检查作品状态、计算版本号、插入版本、创建 Agent Run 和 Review Job、更新作品指针，这些操作必须全成或全败。`SELECT ... FOR UPDATE` 串行化同一作品的提交，避免两个请求都通过 `pending_review` 检查。事务只覆盖数据库写入，不把模型调用放在锁内，防止长事务占锁。

### Q29：当前版本号 `MAX(version_number)+1` 有竞态吗？

同一已有作品在提交路径先锁了 `works` 行，因此同一作品的并发提交会被串行化；此外 `(work_id, version_number)` 有唯一约束兜底。不过其他创建版本的路径也必须锁同一作品，才能保持一致协议。更直接的方案是作品表维护 `next_version_number` 原子递增，或捕获唯一冲突重试。

### Q30：审核通过如何保证发布原子性？

审核结果、finding、版本状态以及 `works` 的正文、质量分和两个版本指针都在同一数据库事务中更新。事务提交前外部读者看不到中间态。如果发布还要写搜索索引、CDN 或消息系统，就不能依赖跨系统事务，应使用 Outbox Pattern 在同一事务写事件，再异步投递并幂等消费。

### Q31：进程内审核队列是怎么工作的，有什么问题？

当前 `enqueueReviewJob` 用进程内 `Set` 防止单进程重复调度，再用 `setImmediate` 异步执行；`runReviewJob` 通过条件更新 `queued → running` 抢占任务，进程重启时把残留 running 重置 queued 并恢复。它适合单实例验证，但多实例下缺少可靠通知、重试退避、死信和租约，重置所有 running 也可能误伤仍在其他实例执行的任务。生产应使用 BullMQ、Redis Streams 或数据库任务表加 `SKIP LOCKED`、lease 和 heartbeat。

### Q32：为什么 `UPDATE ... WHERE status='queued' RETURNING *` 可以充当抢占？

这是数据库原子条件更新：并发 Worker 中只有一个能把同一行从 queued 改成 running 并拿到返回值，其他请求返回空，从而避免同一个 job 同时执行。它解决“领取”竞态，但不能单独解决 Worker 领取后宕机，所以还需要租约超时与重试策略。

### Q33：如何设计审核任务幂等？

入口可以用 `(work_version_id, review_policy_version)` 唯一键，避免同一版本重复建活跃任务；领取任务用原子状态转换；结果落库在事务中先检查预期状态；外部模型调用使用业务 request ID；重试时删除旧 finding 或按 job 唯一约束 upsert。当前代码通过作品 pending 状态和 job 抢占做了部分防重，但还不是完整幂等。

### Q34：为什么互动表主键是 `(user_id, work_id, type)`？

它从数据库层保证一个用户对同一作品同一互动类型最多一条记录，天然适配点赞/收藏开关。接口先删除，若不存在再插入。并发点击下仍可能出现竞态，生产中可以用 `INSERT ... ON CONFLICT DO NOTHING` 与明确的 PUT/DELETE 语义，避免 toggle 接口因重试产生非幂等结果。

### Q35：Feed 查询中的 `COUNT FILTER` 和 `BOOL_OR` 是什么作用？

`COUNT(*) FILTER (WHERE type='like')` 在一次分组中分别聚合点赞和收藏数量；`BOOL_OR(user_id=$currentUser)` 判断当前用户是否做过对应互动，从而避免为每篇文章再查一次，规避 N+1。数据量大后实时聚合会变贵，可以维护计数列或异步聚合表，但要处理一致性和回补。

### Q36：为什么查看文章既更新 `view_count`，又写 `work_view_events`？

`view_count` 适合快速展示累计值，事件表适合按时间窗口做趋势统计。前者是物化计数，后者是事实流水。当前每次查看同步写两次数据库，流量大时可先写事件流、异步聚合，或做批量计数；还要定义去重口径，否则刷新页面会重复计数。

### Q37：项目如何避免 N+1 查询？

Feed 用 JOIN 和条件聚合一次返回作者、计数及当前用户状态；审核详情把 findings、proposals、steps 用 `Promise.all` 并行获取。需要注意“并行查询”只是降低等待时间，不等于减少数据库压力；列表关联应优先用集合查询或 JOIN，且用 `EXPLAIN ANALYZE` 验证索引。

### Q38：有哪些关键索引，为什么这样设计？

例如 `works(status, created_at DESC)` 支持已发布内容按时间筛选排序，`works(user_id)` 支持个人作品查询，`work_reactions(work_id)` 支持作品聚合，`review_jobs(user_id, created_at DESC)` 和 `(work_id, created_at DESC)` 支持审核列表和最新任务，`agent_events(run_id, id)` 支持按运行顺序增量拉取。索引不是越多越好，会增加写放大，应结合真实查询计划调整。

### Q39：数据库迁移为什么不能长期放在应用启动代码里？

`ADD COLUMN IF NOT EXISTS` 方便开发环境自启动，但多实例同时启动、长时间 DDL、失败回滚和版本审计都不好管理。生产应使用版本化迁移工具，把 schema 变更作为部署步骤，支持 expand-contract：先加兼容字段，再双写/回填，最后切读和删除旧字段。

### Q40：RustFS 在项目里承担什么角色？

RustFS 提供 S3 兼容对象存储，用于头像、用户素材和 AI 生成图片；未配置时开发环境降级到本地 uploads。应用保存稳定对象 URL，而不是供应商临时链接。启动迁移会把旧本地资源上传、更新数据库引用，并在成功后删除本地文件，同时修复历史 Markdown 中的旧 URL。

### Q41：对象存储迁移如何保证幂等？

迁移只选择仍以 `/uploads/` 开头的记录；已经转换为对象存储代理 URL 的记录不会再次上传。更新数据库和替换正文引用后再删除本地文件。更严格的生产方案会记录迁移状态与 checksum，采用“上传—验证—事务更新引用—延迟清理”，避免进程在更新与删除之间崩溃。

### Q42：对象存储为什么通常不直接暴露内部地址？

内部 endpoint 浏览器可能不可达，也可能泄露存储拓扑。项目支持公共 URL 或后端 assets 代理。生产中可以使用 CDN、自定义域名或短期签名 URL；公开内容和私有素材应采用不同 Bucket/权限策略，并校验对象 key，防止路径越权。

### Q43：密码存储是怎么做的？为什么不能直接 SHA-256？

密码使用随机 salt 加 `scrypt` 派生哈希，并通过 `timingSafeEqual` 校验。普通 SHA-256 速度太快，攻击者能高吞吐暴力破解；scrypt 是内存困难 KDF，提高离线破解成本。生产还要设置合适参数、密码强度、限流、审计和渐进式算法升级。

### Q44：Refresh Token 为什么数据库只存哈希？

Cookie 中的原始 token 是持有者凭证，数据库只存 SHA-256 哈希和 jti。数据库泄露时攻击者不能直接拿存储值请求刷新；服务端收到 token 后计算哈希比对。Refresh token 本身高熵，哈希无需像用户密码那样使用慢 KDF，但仍需要撤销、过期清理和轮换。

### Q45：注册为什么用了 PostgreSQL advisory lock？

代码在注册事务中获取固定 advisory transaction lock，再检查昵称、手机、邮箱重复，目的是串行化并发注册。数据库还有唯一索引做最终约束，所以 lock 不是唯一安全线。固定全局锁会降低注册吞吐，更好的方式是依赖唯一约束、捕获具体冲突，并只在确有跨行约束时使用细粒度锁。

### Q46：后端当前最需要改进的安全点是什么？

我会优先补四类：请求体 schema 校验和统一大小限制；上传文件 MIME 魔数、尺寸和解码验证；外部图片下载的 SSRF 防护；鉴权接口限流、CSRF 策略和安全响应头。此外，错误日志要避免输出 token、原文敏感信息和供应商响应全文。

## 四、Agent、LLM 与内容审核深挖

### Q47：你如何定义这个项目里的 Agent？它与一次 LLM 调用有什么区别？

一次 LLM 调用只有输入和输出；这里的 Agent 是带状态、步骤、工具、持久化事件和人工决策节点的任务执行单元。`WorkflowRunner` 管生命周期，Workflow 描述业务步骤，`PolicyRetriever` 是工具，`AgentModelGateway` 隔离模型供应商，Run/Step/Event 记录轨迹。即使暂时没有自主循环，它也具备可编排、可观察和可等待用户的 Agent Runtime 特征。

### Q48：为什么不直接使用 LangChain 或 LangGraph？

当前流程固定、步骤少，自研轻量 Runner 能更清楚地控制数据库事务、状态字段和业务语义，避免引入较重抽象。代价是重试、checkpoint、并行节点、补偿和可视化需要自己实现。若后续出现复杂图分支、长时间暂停恢复或多 Agent 协作，可以评估 LangGraph，但应先看是否真正降低维护成本。

### Q49：`WorkflowRunner` 做了什么？

它统一处理 Run 的开始、步骤开始/完成/失败、最终完成、等待用户和失败状态；每个步骤写 `agent_steps`，同时发送 `step_started/step_completed/waiting_user` 事件。具体 Workflow 只负责业务函数，避免每条流程重复写状态机代码。当前不足是步骤失败事件不完整、没有重试策略和真正 checkpoint 恢复。

### Q50：为什么同时设计 Run、Step 和 Event 三层数据？

Run 是任务当前快照，适合列表和状态查询；Step 是结构化执行轨迹，记录每一步输入、输出、耗时和错误；Event 是只追加时间线，适合 SSE 增量消费和审计。只存 Run 会丢历史，只存 Event 每次还原状态成本高，这类似 CQRS 中快照与事件日志的组合，但当前并不是完整事件溯源系统。

### Q51：审核 Workflow 有哪些步骤？为什么按这个顺序？

依次是规范化文本、确定性规则扫描、政策上下文检索、LLM 安全与质量判断、最终政策决策。先规范化可减少 Unicode 和隐藏字符绕过；规则对手机号、身份证等模式提供稳定高召回；检索缩小模型上下文；LLM 判断语境和质量；最后代码合并决策，保证严重规则命中不会被模型轻易降级。

### Q52：为什么内容安全不能只靠敏感词？

敏感词缺乏上下文，会误杀新闻引用、科普和否定表达，也容易被变体绕过；而手机号、身份证等强格式信息又不应完全交给概率模型。合理做法是确定性规则负责明确模式，政策检索提供领域知识，LLM负责语义、意图与解释，再通过代码策略合并结果。

### Q53：为什么也不能只靠 LLM 审核？

LLM 输出具有随机性，可能漏掉格式明确的高危信息，也可能受提示注入影响，且成本和延迟更高。项目把高风险规则作为硬约束：critical 强制 blocked，high 至少 needs_revision。模型是语义判断器，不是不可覆盖的最终裁决者。

### Q54：当前政策检索是 RAG 吗？

广义上是检索增强，因为会从 `review_policies` 取相关规则注入模型上下文；但当前实现是关键词命中、规则类别优先和 top 8 截断，不是向量语义检索。我在面试中会准确说“第一阶段混合规则检索”。演进时可以加 pgvector、BM25/全文检索、政策版本和 rerank，同时保持 Tool 接口不变。

### Q55：为什么检索结果只取 Top 8？

目的是控制上下文长度和噪声，让最相关政策优先。Top K 不是固定真理，应基于标注集调优：K 太小可能漏政策，太大会增加成本并干扰模型。还可以按类别设最低召回、先召回再 rerank，并记录被检索政策版本用于审计。

### Q56：如何防御审核内容中的 Prompt Injection？

把待审核文本明确当作数据而非指令，在 system prompt 中要求忽略原文中的命令；使用结构化输入标签或 JSON；限制工具权限，审核 Agent 不应执行内容中的 URL 或代码；输出只允许固定 schema；最终严重规则由代码合并。高风险场景还应使用专用审核模型或分类器，而不是仅靠提示词。

### Q57：如何保证模型返回结构化 JSON？

网关使用 `response_format: json_object`，随后 `JSON.parse`，再对 decision、分数、severity、confidence、字段长度做白名单和 clamp。这样可以防止一部分格式漂移，但还不够：生产应使用 JSON Schema 或 Zod/Ajv 做完整校验，失败时有限重试并保存原始响应用于排查。

### Q58：模型分数为什么还要 clamp？

即使提示词要求 0～100，模型仍可能返回字符串、负数或超范围值。`clamp` 把可解析数值限制在业务范围，并提供 fallback；finding 的 confidence 同理限制在 0～1。这是“永远不信任外部输出”的边界校验。

### Q59：规则 finding 和 AI finding 直接合并会有什么问题？

同一片段可能被规则和模型重复命中，导致界面重复、风险统计放大。当前实现保留两者以保证信息不丢，但生产应按标准化 excerpt、类别和位置做去重与聚合，同时保留来源字段，便于解释“这是硬规则还是模型判断”。

### Q60：审核准确率怎么评估？

不能用几条 demo 或模型自报分数。应建立人工标注集，按隐私、赌博、诈骗等类别统计 precision、recall、F1，尤其关注高危漏放率；质量审核可评估与人工评分的相关性和分档一致率。还要按规则、检索、模型和合并策略做消融实验，并维护误杀/漏放案例回归集。

### Q61：如果业务更关心“不能漏掉高危”，阈值怎么选？

这是成本敏感分类问题，应提高高危 recall，接受一定误杀，再把灰区送人工复核。阈值应根据验证集的 PR 曲线和业务代价选择，而不是默认 0.5。blocked、needs_revision、approved 可以采用分级阈值，并按类别单独校准。

### Q62：为什么合规改写强调“最小范围替换”？

大段重写可能改变事实、风格和作者意图，也增加用户不信任。改写 Agent 只针对 finding 的原片段生成 replacement，要求不改变无关事实、数字、引用和结构；采用前还检查原片段仍存在，避免把过期建议套到已变化内容上。这是一种乐观并发校验。

### Q63：Human-in-the-loop 是怎么实现的？

改写 Agent 生成 proposal 后，Run 进入 `waiting_user`，不会自动写入线上正文。用户可采用或拒绝；采用会在事务内创建 `source='ai'` 的新草稿版本，记录 accepted 事件；拒绝记录 rejected 事件。当同一 Run 没有 pending proposal 后才完成。模型只提出建议，发布权仍在用户和审核链路。

### Q64：为什么采用建议后不直接发布？

模型改写仍可能引入新风险或事实偏差，所以采用只产生新草稿，之后应再次提交审核。这样保持“任何线上版本都经过审核”的不变量，也让用户有机会继续编辑。

### Q65：`original_content` 字符串替换有什么边界问题？

如果相同片段出现多次，普通 `replace` 只替换第一个，未必是原 finding 的位置；文本轻微变化也会导致失效。当前先检查片段存在，避免盲改。更稳妥的方案是 finding 记录字符 offset、上下文 hash 或 AST 路径，应用时校验版本 ID 与内容 hash，并支持冲突提示。

### Q66：模型网关为什么支持 DeepSeek 和火山方舟？

两者都提供 OpenAI 兼容接口，网关统一 client 创建、模型名和 JSON 生成方法，上层 Workflow 不关心供应商细节。这减少重复拼请求，也便于按环境切换。进一步可以加入能力路由、超时、重试、熔断、成本统计和 fallback，但 fallback 必须考虑不同模型输出分布。

### Q67：模型调用如何设计超时、重试和熔断？

超时用 AbortSignal 限制单次调用；只对网络超时、429、部分 5xx 做指数退避加 jitter，格式错误可低温重试一次，业务拒绝不能重试；用请求 ID 保证结果幂等；连续失败触发按供应商/模型维度熔断，半开探测恢复。重试总预算必须受整个任务 deadline 约束。

### Q68：长对话上下文如何管理？

项目按字符数做保守 token 估算，从总窗口扣除回复、system prompt 和摘要预算，再从最旧消息开始滑动淘汰，至少保留当前轮；旧历史被截断较多时异步生成摘要存入 chat。最终 prompt 顺序是 system、历史摘要、最近消息、当前输入。

### Q69：字符数除以 2 的 Token 估算可靠吗？

它只是面向中英文混合的保守启发式，不等于真实 tokenizer。优点是无额外依赖、速度快；缺点是不同模型和代码/英文场景误差大。生产应使用供应商 tokenizer 或模型对应编码，并监控实际 input tokens；即使精确计数也要保留安全余量。

### Q70：摘要会带来什么信息损失，怎么缓解？

摘要是有损压缩，可能丢失精确数字、用户否定条件或早期承诺，还可能累积幻觉。缓解方式包括把用户偏好、事实和任务状态分槽保存；摘要附来源消息范围与版本；重要事实保留引用；定期从原始历史重建，而不是只对旧摘要递归摘要。原始消息仍应保留，摘要只是推理上下文，不是事实源。

### Q71：文本生成和图片生成为什么统一为一个流式协议？

前端都需要 user_message、status、agent_run、内容增量、done 和 error，只是图片多一个 image 事件。统一协议减少两套状态机和 UI 分支。后端 `route_model` 选择模型，图片先生成临时 URL、持久化，再返回 Markdown 和描述；前端只按事件类型处理。

### Q72：图片生成后为什么还要生成文字描述？

描述可以帮助用户理解和复用图片，也方便把结果作为完整消息存档。代码把描述失败降级为固定提示，不让辅助步骤破坏图片主结果。这体现了关键路径与增强能力分级：图片持久化是主链路，描述是可降级副作用。

### Q73：如何控制 Agent 成本？

首先按任务路由模型，规则能处理的先处理；政策只取相关 Top K；上下文做预算和摘要；记录每个 Run/Step 的模型、token、耗时和重试；对相同版本审核可缓存；设置单任务 max token 和 deadline。成本优化必须同时看准确率，不能为了少调用模型牺牲高危召回。

### Q74：如果模型服务不可用，平台如何降级？

内容创作可以明确提示稍后重试并保留用户消息；内容审核不能在模型失败时默认通过，应保持 failed/pending，不改变线上版本；确定性规则可以先给出部分风险，但不能冒充完整审核。已有线上版本继续服务，新版本等待恢复，这是 fail-closed 的关键发布策略。

## 五、系统设计与八股结合

### Q75：什么是事务的 ACID？项目中如何体现？

原子性体现在提交审核和发布结果要么全部提交要么回滚；一致性由外键、唯一约束和状态规则保证；隔离性通过 PostgreSQL 事务及行锁控制同一作品并发；持久性由数据库提交后落盘机制保证。需要强调，ACID 只覆盖单库，模型调用和对象存储不在同一事务内。

### Q76：PostgreSQL 默认隔离级别是什么？这里会有什么并发问题？

默认是 Read Committed，每条语句看到开始时已提交快照。单纯先查再写可能发生竞态，所以项目对作品使用 `FOR UPDATE`，并用唯一约束兜底。若跨多行维护复杂不变量，可考虑更强隔离级别，但 Serializable 可能产生序列化失败，需要重试。

### Q77：乐观锁与悲观锁有什么区别？项目用了哪些？

`FOR UPDATE` 是悲观锁，预期冲突时先锁住作品；改写 proposal 应用前检查原片段仍存在，类似乐观并发校验。悲观锁直观但会阻塞，乐观锁吞吐高但冲突时要失败重试。更标准的乐观锁可用版本号或内容 hash 写在 `UPDATE ... WHERE version=?` 条件中。

### Q78：Node.js 单线程为什么还能处理高并发？

JavaScript 执行在事件循环线程上，但网络、数据库等 I/O 由系统和运行时异步处理，完成后回调进入事件循环，所以 I/O 密集服务可并发处理大量连接。CPU 密集计算会阻塞事件循环，应使用 Worker Threads、独立服务或任务队列。同步 `scryptSync`、大文件 `readFileSync` 在高并发路径中需要谨慎。

### Q79：事件循环中的 `setImmediate` 是什么？为什么这里使用它？

`setImmediate` 把审核执行放到当前 I/O 周期后的 check 阶段，使 HTTP 提交可以先返回 202，而不等待模型完成。它只实现进程内异步调度，不提供可靠队列语义；进程退出时任务仍可能丢失，所以不能把它描述为消息队列。

### Q80：SSE 在代理层常见什么问题？

反向代理可能缓冲响应、设置较短空闲超时或压缩小块，导致前端不能实时收到。项目设置 `text/event-stream`、`no-cache`、`keep-alive`、`X-Accel-Buffering: no` 并禁用 Nagle。生产还应配置代理超时、周期心跳、断线重连和事件 ID。

### Q81：什么是 Nagle 算法？为什么流式响应会关注它？

Nagle 会合并小 TCP 包以提高带宽效率，但 token 流是很多小块，合并可能增加首字和逐字延迟。`socket.setNoDelay(true)` 倾向立即发送小包。是否有效还受代理、TLS 和浏览器缓冲影响，应通过端到端指标验证。

### Q82：什么是背压？当前 SSE 链路处理了吗？

背压是生产者速度超过消费者处理速度时的流量控制。Node 的 `res.write()` 返回 false 表示内核缓冲区已满，理想情况应等待 `drain` 再继续读取模型流。当前代码没有显式处理，低流量问题不明显，但生产应封装异步 write 并设置缓冲上限，防止慢客户端造成内存增长。

### Q83：如果 SSE 断线，如何做到断点续传？

每个 Agent Event 已有递增 ID，可把事件持久化并在 SSE 中发送 `id:`；客户端重连携带 Last-Event-ID，服务端先回放之后的事件，再订阅新事件。生成文本还要以 chunk event 持久化或定期 checkpoint。当前生成 chunk 没全部进入 `agent_events`，因此现状只能查询任务状态，不能完整恢复文本流。

### Q84：缓存可以放在哪些位置？

政策检索可按政策版本和文本特征缓存，模型审核可按作品版本内容 hash 缓存，公开 Feed 可做短 TTL/CDN 缓存，素材走 CDN。用户态数据和审核中状态不能用粗粒度公共缓存。缓存键必须包含影响结果的模型、prompt、政策版本和租户信息，否则会返回过期或越权结果。

### Q85：如何避免缓存击穿、穿透和雪崩？

击穿可用单飞锁或逻辑过期；穿透可缓存空值、做参数校验或 Bloom Filter；雪崩可给 TTL 加随机抖动、多级缓存并限流降级。对本项目而言，热点 Feed 比单个审核结果更可能出现击穿，审核结果更适合按不可变版本永久缓存并通过版本变化自然失效。

### Q86：如何设计限流？

按用户、IP、接口和模型成本分层：登录用滑动窗口或令牌桶防暴力破解；生成接口限制并发 Run 和每日额度；图片生成权重高于文本；审核提交按作品防重。多实例需要 Redis/Lua 等集中式限流，返回 429、Retry-After 和可解释剩余额度。

### Q87：如何做可观测性？

统一 request ID、user ID（脱敏）、work/version/job/run ID 串起日志；采集首 token 延迟、总耗时、模型错误率、SSE 中断率、队列等待、审核各类别命中、误杀/漏放和对象存储错误；Step 级数据形成 trace。原文和模型输入可能含隐私，日志必须采样、脱敏并设置保留期限。

### Q88：如何设计重试，避免“重试风暴”？

只重试可恢复错误，使用指数退避和随机抖动，限制最大次数和总 deadline；通过幂等键避免重复副作用；服务恢复时限制并发并逐步放量；队列任务设置最大尝试与死信。用户主动取消、参数错误和内容被拒绝不应重试。

### Q89：什么是 Outbox Pattern，项目哪里适合用？

业务事务内同时写业务数据和 outbox 事件，后台可靠投递到消息系统，成功后标记；这样避免“数据库已发布但消息没发出”。审核通过后同步搜索索引、通知、榜单和 CDN 失效都适合 Outbox。消费者必须按 event ID 幂等。

### Q90：如果系统扩展到多租户，要注意什么？

所有业务表增加 tenant_id，并把唯一索引和查询条件纳入租户；鉴权上下文同时验证用户与租户；对象 key、缓存 key、队列和日志隔离；政策库支持平台级与租户级覆盖；数据库可用 Row-Level Security 作为纵深防御。不能只依赖前端传 tenant ID。

## 六、压力追问：作为面试官会继续怎么问

### Q91：你说“可恢复”，但现在真的能从任意步骤继续吗？

严格来说不能。当前 Run、Step、Event 已经提供恢复所需的状态基础，审核任务重启后也会重新入队，但 Workflow 是从头重跑，不是从最后 checkpoint 精确继续。因此更准确的表述是“具备任务状态持久化和重启重跑能力，精确步骤恢复仍待实现”。

### Q92：你说“自动发布”，模型误判怎么办？

当前 approved 会自动提升版本，适合演示闭环；生产策略应按风险分层。低风险高置信内容可自动通过，中间区间进入人工复核，高风险拦截，并提供申诉。模型和规则版本都要记录，支持事后审计和批量回查。

### Q93：如果审核完成时用户已经提交了更新版本，会不会旧版本覆盖新版本？

当前同一作品处于 pending_review 时禁止重复提交，因此常规路径规避了这个问题；但跨路径或未来放开并行审核后，需要发布时做 compare-and-set：只在 `latest_version_id` 仍等于被审版本，或明确根据提交序号判断时才提升，否则把结果标为 superseded，不能让旧任务覆盖新候选。

### Q94：为什么审核原文最多允许 10 万字符？模型上下文一定放得下吗？

接口长度上限只是资源保护，不等于模型 token 预算。10 万中文字符加政策上下文可能接近或超过某些模型限制。生产应按 tokenizer 计数，长文分段审核，再做篇章级汇总；确定性规则可以全文扫描，LLM 使用带重叠窗口的 chunk，并保留位置映射。

### Q95：长文分段审核会漏掉跨段语义吗？

会，所以不能简单独立切块。可以按标题和段落语义切分，保留 overlap；先做块级召回，再把高风险块连同邻近上下文交给模型；最后增加文档级摘要和全局一致性审查。finding 需要映射回原文 offset。

### Q96：热点榜单当前真的有复杂算法吗？

没有。当前 hot 基本按浏览量和时间排序，TODO 才计划综合浏览、点赞、收藏权重。我不会在面试中称其为推荐算法。演进时可设计带时间衰减的 Wilson Score 或加权热度，并通过离线回放和 A/B 实验确定权重。

### Q97：项目里最大的技术债是什么？

第一是后端路由和前端创作页职责过重；第二是缺少系统化测试和 schema 校验；第三是进程内任务队列与不完整恢复；第四是审核评测体系尚未建立；第五是启动时内嵌迁移。我的处理顺序会先补关键链路测试与可观测性，再替换可靠队列，最后做结构性拆分和评测闭环。

### Q98：如果只给你一周做生产化，你怎么排优先级？

先保证“不能错发”：审核失败不发布、版本 CAS、幂等和事务；再保证“任务不丢”：持久队列、重试、死信和超时；然后补 schema 校验、限流、SSRF/上传安全；同时建立核心指标与告警；最后补标注回归集和灰度开关。UI 美化和高级推荐不会优先于数据安全与发布一致性。

### Q99：你个人到底做了哪些？

这题必须按真实贡献回答。我会用“我负责/参与了某一具体链路，关键决策是……，代码落点是……，遇到的问题是……，验证方式是……”来说明，不把整个仓库都说成独立完成。面试前应根据提交记录、PR 和实际协作，把本文问题标注为“主讲、了解、规划”三档。

### Q100：这个项目有什么失败或反思？

前期更关注把功能跑通，导致大组件、大路由和自动化测试不足；审核第一阶段也只是关键词检索加 LLM，不能直接证明准确率。反思是 AI 项目的完成标准不能只是“模型能返回”，还应包含可评测、可追踪、可降级、可恢复和人在环。后续架构正是围绕这些缺口补齐。

## 七、面试话术与备战清单

### 1 分钟项目介绍

> 我参与开发了一个 AIGC 内容创作与审核平台，面向创作者提供多轮文本生成、文生图、素材管理、编辑发布和内容治理。前端基于 Next.js、React、TypeScript 和 Zustand，后端使用 Express、PostgreSQL，并通过 OpenAI 兼容 SDK 接入火山方舟与 DeepSeek。项目中我最想展开的是三条链路：第一，用 SSE 和 AbortController 实现可中断的流式创作，并用滑动窗口与历史摘要控制长对话上下文；第二，用不可变作品版本隔离草稿与线上正文，审核通过后事务化提升发布版本；第三，把确定性规则、政策检索、LLM 结构化审核和 Human-in-the-loop 改写做成可追踪的 Agent Workflow。当前也明确保留了工程边界，例如审核还是进程内队列、检索尚未升级为向量召回、准确率需要标注集验证。

### 推荐主动引导的三条主线

1. 面试官偏前端：引到 SSE 半包/粘包、AbortController、状态分层、编辑器 Markdown 转换与性能优化。
2. 面试官偏后端：引到不可变版本、事务行锁、原子任务抢占、幂等、对象存储迁移和双 Token。
3. 面试官偏 AI：引到规则 + 检索 + LLM 决策合并、结构化输出、Agent 可观测性、人在环与离线评测。

### 避坑提醒

- 不要说“审核准确率很高”，当前没有标注集指标；应说已经设计多层机制，准确率需用 precision、recall、F1 和漏放率验证。
- 不要说“分布式任务队列”，当前是进程内调度加数据库状态抢占；Redis/BullMQ 是演进方向。
- 不要说“向量 RAG”，当前是关键词、类别优先的政策检索。
- 不要说“断点续跑已完成”，当前有运行轨迹和重启重跑，尚无任意步骤 checkpoint 恢复。
- 不要说“推荐算法”，当前 Feed 仅支持浏览量、时间、点赞、质量等排序。
- 不要承诺具体 QPS、DAU、性能提升百分比，除非能提供压测、监控或真实业务数据。
- 不要把所有模块都说成个人独立完成；按 Git 提交、PR 和实际分工描述。
